# Building Data Model — Design

**Date:** 2026-06-18
**Status:** Design (implementation plan to follow via writing-plans). Revised after adversarial review.
**Atlas stratum:** S3 Blueprints (edges to S5 Settlements & Zoning, Materials, and the S1 Claims/permanence kernel)

**Goal:** Turn a building from a flat, single-level footprint into a *named container of stacked floors of typed sub-spaces* — deterministic, lazy, claimed through the **one existing claims system**, quantized into generatable wall-section pieces, and visibly multi-story — without inventing a second permanence model or violating the infinite-world purity contract.

---

## 1. Motivation & current state

Today a building is **flat and single-level**: `generateFootprint` (sim/world/buildings/footprints.js) yields one `{sections, walls, doors, floors, interior, boundingBox}`. The inspector's "4 sections" are *horizontal* pieces of one ground plan, not stories; `Stairs Down` is dead metadata. There is no z-axis, no unit model, no vertical connectivity, no clickable sub-space.

This fills the world-compiler's deferred gap ("apartment … multi-story **implied**"; "interiors **honestly absent** until interior generation lands").

### Two live bugs this resolves as a by-product
- **Overlapping / un-clickable buildings.** Three differently-capped, un-deduped building sets disagree: `getBuildingsNearChunk` (building-tile-query.js:237-254) returns the **full uncapped** 3×3-macro list; the `maxB=Math.min(len,80)` cap lives *separately* in `cachedLayout`'s `floorIndex` (line 82) and `wallIndex` (line 114); and the clickable `9` overlay applies its **own** cap + `globalOccupied` de-overlap. So the draw list, the floor/wall query, and the click set are capped and deduped differently. Plus `sim-debug-overlay.js` hardcodes `WORLD_SEED=42` (a `const` at line 20 plus literal `layoutSettlement(42,…)` calls) while `building-tile-query.js` uses `getWorldSeed()` — they diverge the moment a non-42 seed is set. **Fix:** §8 + the Slice-1 build step produce **one** capped + de-overlapped resolved building set shared by draw list, floor/wall index, labels, and click.
- The `9` overlay dropping names at zoom is unrelated rendering (task #50).

### User-approved requirements
Multi-story-visible in 3/4 top-down (5-story ≠ 1-story; tall runs off-screen; occludes terrain behind — north-wall fix already shipped); per-type façade archetypes; roof = separate subsystem capping only the terminal floor; coherent interiors (every unit reachable from the stair core); deterministic re-enterable interiors (`f(unitId)`, edits = deltas); vertical transit = shared main stair core + private internal stairs in multi-floor units + lift when a building exceeds 3 above-ground floors (mechanism deferred, floor-select interaction); rich shape palette + sprawling complexes; rare bridges/tunnels/arcades.

## 2. Place in the atlas & the purity boundary

- **S3 Blueprints**, ladder `region → settlement → district → building → floor → unit → room → wall-section`. The **terminal `wall-section`** is the *quantized, generatable sprite piece* the atlas (line 48) and CLAUDE.md decision #6 mandate. "Buildings are structures, not sprites" means the structure is *composed of* quantized wall-piece sprites — so floors/units emit `wall-section` nodes; the rendering spec quantizes them to art.
- **Edges:** the S1 **Claims kernel** (one permanence system — §8), Settlements & Zoning (NPC home/work slots — §4/§13 edge), Material System (façade/roof/floor materials).

### The purity boundary (honest, matching existing code)
The infinite-world contract is `pure f(seed, ancestors)` with **no sibling-layer reads** and visit-order independence. The shipped placement code does **not** give per-building purity: `placeBuildings` uses a mutable `occupiedTiles`/running index, and `specializeBuilding` reads-and-mutates `communitySpecializations`. Therefore:

> **The pure generation unit is the `settlement` node.** `layoutSettlement(seed, site, tier, race, biome)` runs the whole settlement in one deterministic pass and is **cached per macro-cell** (as today). Buildings/floors/units/rooms are deterministic **by-products** of that pass and are **materialized lazily for read**, but they are **regenerated by re-running the whole settlement** (from cache), never by a stateful per-building re-roll. Lazy per-building regeneration that reorders the settlement pass is forbidden.

A node reads only `worldSeed`, its own payload, and a **closed `ancestorContext` struct** (§3) of strictly-coarser values — never a sibling node or a sibling-derived aggregate.

## 3. Architecture — the `BlueprintNode`

```
BlueprintNode {
  id:        a canonical PATH TUPLE  [settlementId, 'building', bOrd, 'floor', fIdx, 'unit', uOrd, …]
             (caches and NPC addressing key on the tuple — never a 32-bit hash, which birthday-collides
              ~77k ids at the 1M-entity target; a short hash is display-only)
  kind:      'settlement' | 'district' | 'building' | 'floor' | 'unit' | 'room' | 'wall-section'   // extensible (body assembly later)
  payload:   kind-specific typed data (§4)
  claim:     world tiles this node owns. ONLY the building (and connection, §5.3) claim world space, through
             the S1 claims kernel (§8). Inner nodes (floor/unit/room/wall-section) live inside the building's
             claim (vertical/interior) and never claim independently.
  enumerate(): cheap list of child STUBS (e.g. a floor index range) — O(1)
  materialize(childStub): lazy, cached-by-path: builds that child's payload only on demand
}
```

- **Kind registry:** each kind registers `{ generatePayload(parent, ordinal, ctx), enumerateChildren(node), materializeChild(node, stub) }`. **Enumeration is cheap** (a 100-floor tower's floor range is just `[min..max]`); **materialization is lazy per child and cached by path** — so an untouched tower materializes O(1) nodes and "touching floor N never builds N+1."
- **`ancestorContext` is a closed, read-only struct enumerated per kind** (e.g. a floor's context = `{settlementTier, buildingType, buildingShape, floorIndex, useFromStackPlan, settlementDemand?}`). It may contain only seed + strictly-coarser values computed before the sibling layer exists. Passing any sibling node or sibling-derived value is forbidden (enforced by lint/test).
- **Determinism:** same seed ⇒ same settlement pass ⇒ same building → floors → units → rooms, visit-order independent. This is what guarantees "same room every time."
- **Today's code maps in:** the flat footprint becomes the `building` node's shell payload; `generateFootprint` continues to return its existing fields for back-compat during migration (§12) and additionally exposes the node. The single `interior` record is replaced by per-unit lazy `room` interiors.

## 4. Node ladder & payloads

**building**
```
id (path), name|brand, owner, buildingType, race, tier, age, condition(delta-driven)
shape            = { archetypeId, sizeTier }                 // abstract generator choice (§5)
requestedFootprint = { sections[], walls[], doors[], floors[] }  // concrete geometry realized FROM shape, PRE-claim
effectiveFootprint  // = requestedFootprint minus claim-lost tiles; computed on read via §8 (not the only stored form)
facadeArchetype  // exterior recipe ref (materials, window/balcony/setback pattern) — read by the render spec
roofRef          // §9.3 — caps the terminal floor of EACH terminal wing/section (compound shapes → multiple caps)
floorRange       = [minFloor … maxFloor]   // minFloor ≤ 0 (basements); maxFloor ≥ 0
aboveGroundFloors = count of indices ≥ 0     // <-- this is what "floorCount" means for the lift rule
floorStackPlan   // the per-index use-band plan (basement→ground→commercial→residential), computed ONCE here so
                 // floors read their .use from this ancestor field and never consult sibling floors
stairCores[]     // one fixed core per connected vertical column (§6); each = footprint cell(s), same on every floor of its column
liftCore?        // present iff aboveGroundFloors > 3 — reserved shaft cell(s) + mechanismId (opaque string → §9.4 lift subsystem)
connections[]    // refs to §5.3 connection nodes that attach here (generated by the owning district/settlement, not by this building)
claim            // world tiles owned via the S1 claims kernel (§8)
```

**floor** (lazy child of building, one per index in `floorRange`)
```
index, use (read from building.floorStackPlan[index]), circulation (walkable region), facadeBand
```

**unit** (lazy child of floor; may span floors)
```
id (path), unitKind (apartment|single-house|shop/business|lobby/common|storage|crypt|…)
name|brand, owner, occupancySlots {home?, work?}   // NOMINAL capacity — see §4.1
doorTile (onto the floor circulation)
subFloors?   // a MULTI-FLOOR unit is a nested mini-building: its own floors + a PRIVATE internal stair,
             // entered once from the main core. Recursion is capped at ONE level (a unit inside a tower may
             // not itself contain multi-floor units) — enforced in the generator.
```

**room** (lazy leaf)
```
baseline interior (tiles/partitions/furniture/materials) = pure f(worldSeed, unit.id) ONLY — excludes delta-driven fields.
final state = ordered fold of deltas over that baseline (§8 delta order). Identical every visit.
```

**wall-section** (terminal quantized shell piece)
```
the generatable sprite primitive: a wall/facade/door/window segment emitted by a floor's shell, at a position,
with material + opening type. The rendering spec quantizes these to art; this spec defines them as the structural
leaf so multi-story walls/facades have a generatable unit (atlas requirement).
```

### 4.1 occupancySlots — edge to Society (honest absence)
`occupancySlots` are **nominal capacity**, generated supply-side from `buildingType × tier × centrality`. **Society is authoritative for realization** — an unfilled tower is honest emptiness, not a contradiction. Optionally, building generation MAY read a coarser **settlement demand** aggregate (household/economy counts from the chronicle/L2 layer) via `ancestorContext` to scale floor/unit counts; if present it is an ancestor read (permitted), if absent slots remain nominal. This spec does **not** assign NPCs to slots.

## 5. Footprint shapes, sizes, complexes, connections

### 5.1 Shape palette
A building's `requestedFootprint` is a **union of rectangular sections** (today's representation, generalized). The generator picks a **shape archetype** by `buildingType + seed`:
- **Simple:** Square, Rectangle. **Complex single:** L, T, U-court, Cross, Courtyard (hollow ring), H-block, Octagon, Round tower, Cruciform (nave+transept), Stepped.
- **Sprawling complexes** (big civic/market/palace/campus): Twin-wing hall, Double-court bazaar, Campus cluster (blocks + connecting corridors), Long arcade — produced by **compounding** sections + corridors.

### 5.2 Size & centrality
`sizeTier ∈ {small, medium, large}` sets the tile span (more tiles = bigger). **`centrality ∈ [0,1]`** = normalized inverse distance from the lot to the settlement core, read deterministically from district/lot `ancestorContext`. Size and floor count scale with `buildingType × tier × centrality`.

### 5.3 Inter-building connections (rare)
A **connection** (skyway bridge = upper floor; tunnel = basements; covered arcade = ground) links two buildings. **It is generated by the coarser `district`/`settlement` node that owns both endpoints** — never by a building reaching sideways to a sibling — so it resolves identically from either end regardless of materialization order. A connection **claims its own passage tiles at the lowest building-tier priority** (must not steal endpoint footprint tiles) and records the floor index it attaches to at each end. **Honest absence:** traversing a connection is the Traversal/Interaction system's job, not this spec.

## 6. Vertical structure & circulation

- **Floor count = f(buildingType profile, tier, centrality)** — house 1–2, shop 1–2, inn 2–3, apartment 3–N, civic/temple grand, watchtower tall; ~100 floors is a **rare** great-city landmark. The lift rule uses **`aboveGroundFloors` (index ≥ 0)**.
- **Floor-use mix** = `building.floorStackPlan`, computed once on the building (basement storage → ground lobby/shopfront → lower commercial → upper residential; house = 1–2 all-residential; temple = crypt → hall → galleries). Floors read `.use` from it by index.
- **Circulation-first partition (coherence guarantee):** per floor — (1) place the column's stair core, (2) grow a circulation region from it, (3) partition the remainder into units by `unitKind`, (4) give each unit a `doorTile` onto circulation. **Validity = every unit reachable from the core.** Retry is **bounded at a fixed K** (seeded by attempt index); on exhaustion a **deterministic terminal fallback** applies (the single-unit-floor rule: one unit absorbs the stair into its hall) so the function is **total and pure**.
- **Stair core selection (deterministic, basement-safe):** the core tile must lie in the **intersection of every floor's interior cells across the whole column** (so a basement+ground column with differing setbacks still shares it); within that intersection pick the **centroid-nearest** cell (documented tie-break). Ground (index 0) always exists (`maxFloor ≥ 0`). **If the intersection is empty**, the deterministic fallback demotes to **per-floor cores with a recorded vertical break** (or clamps the column footprint to the shared interior) — total, never throws. Tested: the core is a floor (not wall/door/exterior) tile on every floor of its column, including a constructed basement+ground differing-setback case.
- **Vertical transit:** (1) **main stair core(s)** — one per connected vertical column (a sprawling complex with disjoint wings gets one core per wing-column), fixed tiles every floor of that column; (2) **private internal stairs** inside multi-floor units; (3) **lift** reserved **iff `aboveGroundFloors > 3`** (locked) — own shaft + opaque `mechanismId` (§9.4) + floor-select interface.
- **Roof for complexes:** `roofRef` caps the terminal floor of **each terminal wing/section**, so no wing is left uncapped.

## 7. Generation (deterministic) — Part A

Generation is the settlement pass (§2) producing, per building, its `floorStackPlan`, `stairCores`, `liftCore`, and per-floor partitions — all pure over `worldSeed + node payload + closed ancestorContext`, with **no sibling reads** and **enumerate-then-lazily-materialize** children. Interiors generate on the **raw `requestedFootprint`** (never the claim-clipped one — §8). Identity (`unit.id` path) and `occupancySlots` are emitted for Society.

## 8. Claims & permanence — Part B (ONE system, not a new one)

**Register buildings into the one permanence kernel — do not invent a parallel resolver.** *Code reality:* today `src/world/decoration-claims.js getClaimMask()` simply ORs the F3–F6 flora ellipse masks (no priority tiers, **no architecture slot**), and buildings suppress flora **only** through the mutable, renderer-populated `buildingClaimTiles` Set (line 553), read at `isClaimedAt`, `f4/f5/f6Placements`. So the architecture tier is **net-new (small) work**, not a pre-reserved slot: add a **pure `architectureClaimAt(wx,wy)` predicate** backed by the resolved building set and call it at those same sites — a building hit means the tile is fully claimed (skip flora rasterization). This is the highest-priority claimant (above F6); a whole-tile building claim fills all 64 sub-cells; roads register here later the same way.

- **Delete the mutable `buildingClaimTiles` Set** (renderer-populated, non-pure). Flora suppression and the resolved building set both derive from the **pure** `architectureClaimAt` predicate keyed by the resolved set, with **no renderer mutation**. Producers call `setArchitectureClaim(predicate)` (main thread after the renderer resolves; worker after `building-tile-query` resolves); changing the predicate `clearClaimCaches()`. (`decoration-claims.js`, `building-renderer.js`, `sim-debug-overlay.js` are on the §12 edit list.)
- **Building claims bypass the flora scan radius.** A large building (tens–hundreds of tiles) can never be found by the radius-limited flora neighbor scan (`claimScanRadius`, capped ~8 tiles for ~6-tile flora). `architectureClaimAt` is a **direct O(1) point-in-footprint test** against the resolved set for the tile's macro neighbor ring, evaluated **before** any flora scan.
- **Cross-settlement de-overlap — tile-level, deterministic owner tie-break (not rect clamping).** Resolve all buildings into **one set** by walking settlements in a fixed order (sort by `(mx,my,x,y)`, then building index) into a global occupied set; the **first writer wins** a contested tile, identically regardless of which range/side the query came from (this mirrors the overlay's existing `globalOccupied` sweep at `sim-debug-overlay.js:294-307`). Losing a stair/door tile **demotes the whole building** (never a silent partial clip — §8 raw-footprint rule). `genesis.territoryAround` is *centered with no deconfliction*, and `MIN_SPACING` already separates surviving large settlements, so this tile-level sweep is the real de-overlap — no fragile rect math. The shared **neighbor ring must cover the largest footprint**: `R = ceil(MAX_SETTLEMENT_RADIUS / MACRO_TILES) = ceil(220/64) = 4` → a **9×9 macro ring (−4..+4)** (radius-3/7×7 would undercover a `world_capital` and reintroduce the boundary bug), shared by every consumer (replaces the `−1..+1` scans in `building-tile-query.js`); a §11 test pins R so the largest tier resolves identically from `MAX_SETTLEMENT_RADIUS` away.
- **Interiors use the raw footprint.** Claim loss only suppresses **render/collision** on lost tiles. If a claim would remove a **stair-core or door** tile, that is a deterministic, neighbor-independent **demotion/removal of the whole building** (never a partial clip that silently breaks circulation). Tested: no generated `doorTile`/`stairCore` is ever a claim-lost tile.
- **Permanence:** edits (furniture move, board-up, destruction) are **deltas** over the immutable baseline, applied as a **pure fold in a total content-addressed order** (sort by `tick asc, deltaId asc`) — independent of arrival/cache state — so "same room every time" holds even for edited rooms after cache eviction + regeneration. The baseline room generator's inputs **exclude** delta-driven fields.

## 9. Rendering & interaction — Part C (DECLARED SEPARATE; hooks only)

This spec is **data model + generation**. Separate specs consume the hooks:
1. **Exterior multi-floor rendering** — façade stacker (height = `aboveGroundFloors` + basements shown appropriately, setbacks, balconies, per-floor `facadeBand`, occlusion); quantizes **`wall-section` nodes** to sprites. *Own spec.*
2. **Interior rendering + movement** — **one floor at a time** on the 3/4 camera; stair = slide to adjacent floor; lift = floor menu. Model provides per-floor interiors, unit doors, stair/lift tiles. *Own spec.*
3. **Roof system** — `roofRef`; per-wing caps. *Own spec.*
4. **Lift mechanism** — concrete device for `mechanismId`. *Own spec.*
5. **NPC home/work assignment** — Society consumes `occupancySlots`. *Honest absence.*
6. **Rich room content** — beyond the lazy `room` contract here. *Own pass.*
7. **Connection traversal.** *Traversal/Interaction spec.*

Settlement-node-pure, cached per macro-cell; closed `ancestorContext`; enumerate-then-materialize lazy children keyed by path tuple; one claims kernel; delta-over-baseline with total content-addressed order.

## 11. Testing — Part D (assertable predicates)

- **Determinism:** same node path ⇒ byte-identical floors/units/rooms across repeated generation (deepEqual, matching the existing suite's bar). Building-claim resolution is byte-identical **with no renderer call having run** (proves `buildingClaimTiles` removal).
- **Seed:** with a **non-42** seed, the overlay's resolved building set == the tile-query's resolved set (same ids/tiles).
- **Lazy:** instrumented counter shows requesting floor N built payloads only for N + ancestors; an untouched 100-floor tower materializes O(1) nodes; a multi-floor unit's nested `subFloors` generate lazily and recursion depth never exceeds 1.
- **Claims:** after resolution, no two buildings' effective footprints share a tile across settlement/macro boundaries; resolution identical from either side; a `world_capital` building near a macro boundary resolves identically from `MAX_SETTLEMENT_RADIUS` away; largest-tier footprint ⊆ the neighbor ring.
- **Lift/floors:** `liftCore present ⟺ aboveGroundFloors > 3` (both directions); mean floor count increases monotonically across the ordered tier list; `P(floorCount ≥ 20)` below an explicit cap over a large sample.
- **Circulation:** every unit's `doorTile` is flood-fill-reachable from a stair core; the bounded-retry fallback fires and still yields a connected, door-reachable floor for adversarial compound/courtyard footprints; no `doorTile`/`stairCore` is a claim-lost tile.
- **Shapes:** every footprint is a connected section-union with ≥1 perimeter door; size scales monotonically with tier.
- **Deltas:** apply two conflicting deltas, evict, regenerate ⇒ identical resolved room state regardless of record order.
- **Connections:** a skyway resolves identically approached from either endpoint (no materialization-order dependence).
- ** id:** a dense city's full unit set has zero path collisions.
