Spatial Compiler: How primitives map to joints

The same instruction produces different joint angles depending on which bone in the chain it targets

Example: "raise left_arm, amount: 0.8"

What the LLM says:
{
  part: "left_arm",
  action: "raise",
  amount: 0.8,
  ticks: 4
}
What the compiler outputs:
{
  arm_u_l: -136,  // 80% of [-170, 0]
  arm_f_l: 0,     // stays straight
  hand_l: 0       // stays neutral
}
"raise" on upper arm = rotate toward overhead
forearm + hand follow naturally (0 = straight)

The Mapping Rules

Direction-Dependent Draw Order (Z)

The same "extend left_arm forward" looks different from each direction — not because the joints change, but because of what's visible:

SOUTH (front)
Arm extends TOWARD camera
→ foreshortens (shrinks)
→ draws IN FRONT of torso
xProj: 1.0
EAST (profile)
Arm extends ACROSS screen
→ fully visible length
→ draw order: same layer
xProj: 0.25
NORTH (back)
Arm extends AWAY from camera
→ foreshortens (shrinks)
→ draws BEHIND torso
xProj: 1.0
SE (diagonal)
Arm extends PARTIALLY across
→ partial foreshortening
→ near arm in front, far behind
xProj: 0.75

Key Insight: Joint angles DON'T change per direction

The same joint angles render correctly from all 8 directions because the renderer's xProj/xSign/draw-order already handles the projection. The spatial compiler only needs to compute joints ONCE — the direction system does the rest.

Exception: "extend forward" may need slight draw-order hints for the renderer (e.g., "this arm is reaching toward the camera") so the painter order can adjust dynamically.
