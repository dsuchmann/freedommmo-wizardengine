4655| ## 4. Placement Engine
4656| 
4657| ### 4.1 Two-Layer State Model
4658| 
4659| **Layer 1: Deterministic Baseline** — Given `world_seed + chunk_position`, the placement engine always produces the exact same arrangement of objects. Same seed = same forest, same rocks, same flowers. This is pure math (Perlin noise with fixed seeds). Never stored — regenerated on load.
4660| 
4661| **Layer 2: Delta Log** — Every mutation (player chops tree, NPC digs hole, lightning strikes) is recorded as a sparse delta against the baseline. Deltas decay over time — the world heals itself.
4662| 
4663| ### 4.2 Placement Pipeline
4664| 
4665| ```
4666| For each chunk (32×32 cells):
4667| 
4668| 1. BIOME PASS
4669|    Read biome_id per cell from world compiler ChunkData.
4670| 
4671| 2. AFFINITY LOOKUP
4672|    Load BiomeAffinity for each biome present in chunk.
4673| 
4674| 3. ELIGIBILITY FILTER
4675|    For each cell × each object_pool in its biome affinity:
4676|    - elevation in range?
4677|    - moisture in range?
4678|    - slope below max?
4679|    - distance rules satisfied? (water_distance, road proximity from ChunkData)
4680|    → produces eligible_pools[cell] = list of candidates with weights
4681| 
4682| 4. DENSITY SAMPLING
4683|    For each eligible pool:
4684|    - sample noise field (cluster_mode determines noise type)
4685|    - noise seeded by world_seed + object_id hash (consistent per object type)
4686|    - multiply by pool.density × cell.vegetation_density / 255
4687|    - threshold check → place or skip
4688| 
4689| 5. TRANSITION BLENDING
4690|    For cells near biome boundaries:
4691|    - detect boundary via neighbor biome mismatch
4692|    - compute blend_t = distance_into_transition / blend_width
4693|    - fade biome_a pool densities by (1 - blend_t)
4694|    - fade biome_b pool densities by blend_t
4695|    - inject edge_objects from BiomeTransition definition
4696| 
4697| 6. INSTANCE GENERATION
4698|    For each placed object:
4699|    - select lifecycle phase from lifecycle_distribution (weighted random, seeded)
4700|    - select visual variant (1..variant_count, seeded)
4701|    - apply individuality variance (scale, lean, color shift from instance_seed)
4702|    - instance_seed = hash(world_seed, chunk_x, chunk_y, cell_x, cell_y, object_id)
4703|    → produces ObjectInstance record
4704| 
4705| 7. COLLISION REGISTRATION
4706|    Blocking objects register in pathfinding grid.
4707| ```

4730| ### 4.4 Delta Log with Entropy Decay
4731| 
4732| ```json
4733| {
4734|   "position": [1423, 872],
4735|   "object_id": "oak_tree",
4736|   "mutation": "chopped",
4737|   "new_state": "stump",
4738|   "timestamp": 10045,
4739|   
4740|   "decay": {
4741|     "type": "regrow",
4742|     "recovery_time": 720,
4743|     "stages": [
4744|       { "at": 0.0,  "state": "stump" },
4745|       { "at": 0.3,  "state": "sprouting_stump" },
4746|       { "at": 0.6,  "state": "sapling" },
4747|       { "at": 1.0,  "state": null }
4748|     ]
4749|   }
4750| }
4751| ```
4752| 
4753| **Decay types:**
4754| - `regrow` — living things grow back (trees, grass, flowers). Full lifecycle restarts.
4755| - `fill` — holes/pits fill in over time. Rain accelerates.
4756| - `erode` — exposed structures weather away. Abandoned walls crumble.
4757| - `permanent` — suppressed while a structure occupies the tile. Settlements prevent regrowth. If structure is removed, decay type reverts to `regrow`.
4758| 
4759| **On chunk load:**
4760| 1. Regenerate deterministic baseline (same objects, always)
4761| 2. Load delta log for this chunk from persistent storage
4762| 3. For each delta: elapsed = current_game_time - timestamp
4763| 4. If elapsed >= recovery_time → discard delta, baseline reasserts
4764| 5. If elapsed < recovery_time → compute progress, apply appropriate stage state
4765| 
4766| **Storage cost:** Proportional to how much the player has changed the world. A virgin world = zero delta data. A heavily explored world accumulates deltas, but entropy continuously prunes them.
4767|

4769| 
4770| | Action | Delta | Decay |
4771| |--------|-------|-------|

4782| ## 5. Animation Framework
4783| 
4784| ### 5.1 Animation Resolution Priority
4785| 
4786| When the renderer displays an object, it resolves animation through a priority stack:
4787| 
4788| ```
4789| 1. ACTIVE EFFECT     — object is burning/frozen/being chopped right now
4790|                        → play one-shot or looping effect animation
4791|                        
4792| 2. STATE REACTIVE    — object recently changed state (cracked, wilted, bloomed)
4793|                        → play transition animation, then fall through to ambient
4794|                        
4795| 3. ENVIRONMENTAL     — wind/rain/weather active
4796|                        → blend environmental animation with ambient
4797|                        → intensity scales with weather system values
4798|                        
4799| 4. AMBIENT           — default idle loop
4800|                        → select variant based on time_of_day + season
4801| ```

4806|

4809| - **additive** — color/light effect blended additively (glow, frost shimmer, firefly)

5098| # Biome Layer Stack Design
5099| 
5100| **Date:** 2026-05-29
5101| **Status:** Draft
5102| **Scope:** Extends terrain-object-system-design (2026-05-28) with ordered layer placement, 100% tile coverage, and massive variant generation
5103| **Prerequisite:** 2026-05-28-terrain-object-system-design.md (approved)
5104| 
5105| ## Problem Statement
5106| 
5107| The current placement engine treats all objects as a flat probability pool. Each tile has a random chance of getting any object from the biome's affinity list. This produces sporadic, incoherent placement — scattered sprites on a visible green grid. The base terrain tile (layer 0) is the dominant visual on most tiles.
5108| 
5109| The target is CrossCode-quality environments where every tile is densely layered with multiple overlapping objects that compose into a believable landscape.
5110| 
5111| ## Core Concept: Ordered Layer Stacks
5112| 
5113| Each biome defines an **ordered stack of layers**. The placement engine iterates layers bottom-to-top. Lower layers guarantee 100% tile coverage. Upper layers are progressively sparser.
5114| 
5115| Every layer except layer 0 is composed of **objects with alpha channels** (not tiles). They stack visually — you see through each layer to the layers beneath. This creates depth that flat tiles cannot achieve.
5116| 
5117| ### Universal Rule
5118| 
5119| **Layer 0 must NEVER be the only visible thing on any tile.** If a player can see the raw base terrain tile without at least one object layer on top, the placement has failed.
5120|

5369| ## Placement Engine Changes
5370| 
5371| ### Current Architecture (replace)
5372| 
5373| The current placement engine (`scripts/core/terrain_objects/placement_engine.gd`) iterates all object pools for the biome and probabilistically places each one. This produces flat, sporadic placement.
5374| 
5375| ### New Architecture
5376| 
5377| ```
5378| For each chunk (64×64 tiles):
5379|   1. Determine biome_id for each tile
5380|   2. Load biome_layers/{biome_id}.json
5381|   3. For each layer (bottom to top):
5382|      a. For each tile in the chunk:
5383|         - Roll against layer.coverage
5384|         - If coverage hit (or coverage == 1.0):
5385|           - Select object from layer.objects using weighted random
5386|           - Select variant (1..variant_count, seeded deterministically)
5387|           - Apply sub-tile jitter for natural placement
5388|           - Create ObjectInstance at this layer's z_offset
5389|         - For cluster_mode layers:
5390|           - First pass: place cluster centers using Poisson disk
5391|           - Second pass: fill each cluster with objects
5392|   4. Return all instances across all layers
5393| ```
5394| 
5395| ### Performance Considerations
5396| 
5397| With 100% coverage on 3+ layers across 64×64 = 4096 tiles:
5398| - Layer 1: 4,096 objects
5399| - Layer 2: 4,096 objects
5400| - Layer 3: 4,096 objects
