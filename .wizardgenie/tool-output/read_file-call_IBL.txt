1401| ## Core Principle: Deterministic World From Seed
1402| 
1403| The entire world is defined by a single integer seed. The same seed + coordinates produce the exact same terrain on every client, every time. No server-side terrain storage needed. No pre-rendering needed. The seed IS the world.
1404| 
1405| - World seed: stored in `ServerConfig` (default: 42)
1406| - World capacity: 6,400 × 6,400 chunks = ~41 million chunks
1407| - Each chunk: 64×64 tiles at 32px = 2,048×2,048 pixels
1408| - Total world: ~13 million pixels per side
1409| - Walking time to cross: ~33 hours continuous
1410| - Only ~25 chunks loaded at any time
1411| 
1412| ## 1. Overmap
1413| 
1414| A 6,400×6,400 pixel Image where each pixel represents one chunk. Generated by evaluating the elevation + climate noise functions at each chunk's center world coordinate. Pixel color encodes biome type.
1415| 
1416| ### Generation
1417| - Sample elevation noise at `(chunk_x * 64 + 32, chunk_y * 64 + 32)` for each pixel
1418| - Sample climate noise at the same position for temperature/precipitation
1419| - Classify biome from elevation + climate (same thresholds as BiomeLayer)
1420| - Set pixel color from BiomeLayer.biome_color()
1421| - Total: 41M noise evaluations. Target: ~30 seconds.
1422| - Cache result as PNG at `user://overmap_{seed}.png` for instant reload
1423| 
1424| ### Display
1425| - TextureRect on a CanvasLayer overlay
1426| - Press `M` to toggle open/close
1427| - Red marker shows current player position (updated from player world pos / chunk pixel size)
1428| - Click a pixel to teleport (see Section 3)
1429| 
1430| ### Biome Colors (same as BiomeLayer)
1431| | Biome | Color |
1432| |-------|-------|
1433| | Ocean | Dark blue (0.1, 0.2, 0.5) |
1434| | Beach | Tan (0.9, 0.85, 0.6) |
1435| | Grassland | Green (0.4, 0.75, 0.3) |
1436| | Forest | Dark green (0.15, 0.5, 0.15) |
1437| | Desert | Sandy (0.85, 0.75, 0.45) |
1438| | Mountains | Gray (0.55, 0.55, 0.55) |
1439| | Tundra | White-blue (0.7, 0.75, 0.8) |
1440| | Swamp | Murky green (0.3, 0.4, 0.25) |
1441| 
1442| ## 2. Chunk Streaming
1443| 
1444| ### Loaded Grid
1445| - 5×5 grid of chunks around the player (25 chunks loaded)
1446| - Each chunk rendered via TileMapTerrainRenderer onto shared TileMapLayer nodes
1447| - Total visible area: 320×320 tiles = 10,240×10,240 pixels
1448| 
1449| ### Movement Detection
1450| - Every frame, compute which chunk the player is in
1451| - When player crosses 60% toward a grid edge, trigger loading of the next row/column in that direction
1452| - Loading happens one chunk per frame via `await get_tree().process_frame`
1453| 
1454| ### Chunk Lifecycle
1455| ```
1456| Player approaches edge
1457|   → ChunkStreamer._check_grid_expansion()
1458|   → For each new chunk position:
1459|       → ChunkCache.try_load(cx, cy)
1460|         → HIT: deserialize ChunkData from binary, skip compilation
1461|         → MISS: compile via two-phase pipeline (see below)
1462|       → TileMapTerrainRenderer.register_chunk(chunk)
1463|       → TileMapTerrainRenderer.render_chunk(chunk)
1464|   → Unload chunks > 3 rows behind player:
1465|       → TileMapTerrainRenderer.clear_chunk(cx, cy)
1466|       → Remove from renderer._chunks dictionary
1467| ```
1468| 
1469| ### Incremental Two-Phase Compilation
1470| When streaming (not bulk-compiling), new chunks compile using neighbor context:
1471| 
1472| 1. **Phase 1**: ElevationLayer + OceanMaskLayer compile on the new chunk (uses world_seed noise — inherently seamless)
1473| 2. **Edge propagation**: Copy ocean_distance values from already-compiled neighbor chunks' edges into the new chunk's border cells, then run local BFS inward. This replaces the global BFS with O(chunk_edge) work.
1474| 3. **Phase 2**: ClimateLayer + BiomeLayer + VegetationLayer + CoastalLayer compile using the corrected ocean_distance data
1475| 
1476| This produces seamless terrain without needing all chunks compiled upfront.
1477| 
1478| ### Performance Budget
1479| - Chunk compilation: ~50ms (GDScript)
1480| - Chunk rendering: ~20ms (TileMapLayer.set_cell)
1481| - At 1 chunk per frame (60fps): ~70ms per chunk = fine, no frame drops
1482| - Streaming 5 new chunks (one row): ~5 frames = 83ms total
1483| - Player walking speed: 3.4 tiles/sec = crosses a 64-tile chunk every ~19 seconds
1484| - 19 seconds between row loads. Plenty of buffer.
1485| 
1486| ## 3. Click-to-Teleport
1487| 
1488| When overmap is open and player clicks:
1489| 
1490| 1. Map pixel (px, py) → chunk coordinates (px - 3200, py - 3200)
1491| 2. Clear all loaded TileMapLayer cells
1492| 3. Show "Traveling..." label
1493| 4. Compile 5×5 grid around target chunk (~25 chunks, ~1.25 seconds)
1494| 5. Teleport player to center of target chunk
1495| 6. Close overmap, resume gameplay
1496| 
1497| Player position marker on overmap: `marker_pos = player_world_pos / (ChunkData.SIZE * TILE_SIZE)`
1498| 
1499| ## 4. Binary Chunk Cache
1500| 
1501| ### Format
1502| ```
1503| u32 magic (0x434B4E4B = "CHNK")
1504| u16 version (1)
1505| i32 chunk_x
1506| i32 chunk_y
1507| i32 world_seed
1508| u16 size (64)
1509| [PackedFloat32Array elevation — 4096 floats]
1510| [PackedByteArray ocean_mask — 4096 bytes]
1511| [PackedFloat32Array ocean_distance — 4096 floats]
1512| [PackedFloat32Array temperature — 4096 floats]
1513| [PackedFloat32Array precipitation — 4096 floats]
1514| [PackedByteArray biome_id — 4096 bytes]
1515| [PackedByteArray vegetation_density — 4096 bytes]
1516| [PackedByteArray vegetation_species — 4096 bytes]
1517| [PackedFloat32Array slope — 4096 floats]
1518| ```
1519| 
1520| ### Storage
1521| - Location: `user://chunks/{cx}_{cy}.bin`
1522| - Size per chunk: ~70KB (mostly float arrays)
1523| - 1000 cached chunks = ~70MB (reasonable)
1524| - Seed validation: if cached chunk's world_seed doesn't match current seed, discard and recompile
1525| 
1526| ### Cache Policy
1527| - Save after first compilation
1528| - Load on revisit (skip compilation)
1529| - Invalidate when world_seed changes
1530| - No size limit — disk is cheap, player exploration is valuable
1531| 
1532| ## 5. File Architecture
1533| 
1534| | Component | File | Lines (est.) | Responsibility |
1535| |-----------|------|-------------|----------------|
1536| | CleanWorld.gd | Existing (~180 lines) | ~250 | Scene controller: player, camera, bokeh, overmap toggle, teleport |
1537| | OvermapGenerator | `scripts/core/overmap_generator.gd` (new) | ~120 | Generate 6400×6400 Image from noise. Cache as PNG. |
1538| | ChunkStreamer | `scripts/core/chunk_streamer.gd` (new) | ~200 | Manage 5×5 grid. Detect movement. Compile/load/unload chunks. |
1539| | ChunkCache | `scripts/core/chunk_cache.gd` (new) | ~150 | Binary serialize/deserialize ChunkData. File I/O. |
1540| | WorldCompiler | Existing | Unchanged | Compile chunks from layers |
1541| | TileMapTerrainRenderer | Existing | Unchanged | Render chunks to TileMapLayers |
1542| 
1543| **Data flow:**
1544| ```
1545| Player moves → ChunkStreamer detects edge approach
1546|   → ChunkCache.has(cx, cy)?
1547|     → YES: ChunkCache.load() → skip compilation
1548|     → NO: WorldCompiler two-phase compile → ChunkCache.save()
1549|   → TileMapTerrainRenderer.render_chunk()
1550|   → Unload distant chunks
1551| 
1552| Player presses M → OvermapGenerator.get_or_create() → display overlay
1553| Player clicks overmap → CleanWorld._teleport_to(chunk_x, chunk_y)
1554|   → Clear grid → compile 5×5 → render → teleport
1555| ```
1556| 
1557| ## 6. What This Does NOT Include
1558| 
1559| - Rivers (need cross-chunk flow simulation — separate effort)
1560| - Settlements, buildings, NPCs (Layers 2-7 — future work)
1561| - Multiplayer synchronization (same seed = same world, but player positions need networking)
1562| - Sound or music (future layer)
1563| 
1564| This spec covers ONLY: overmap generation, chunk streaming, click-to-teleport, and binary caching — all operating on the existing Layer -2 terrain pipeline.

1567| # Tile Object Stack + Atomic Asset System
1568| 
1569| **Date**: 2026-05-25
1570| **Status**: Active
1571| **Depends on**: World Compiler (2026-05-24), BuildingCompiler
1572| 
1573| ## Problem
1574| 
1575| The world compiler places buildings as single-type tiles (one wall OR one floor per position). Real buildings need stacked objects per tile — a floor with a rug on it, a table on the rug, a plate on the table, a spoon on the plate. Each object has properties (walkable, pickable, interactable). The current system can't represent this.
1576| 
1577| Additionally, PixelLab generates whole buildings as single images. We need it to generate **atomic pieces** — thousands of walls, doors, floors, furniture — that assemble into unique buildings programmatically.
1578| 
1579| ## Architecture Overview
1580| 
1581| Three subsystems:
1582| 
1583| 1. **TileObjectStack** — each world tile holds an ordered stack of objects with properties
1584| 2. **AssetCatalog** — JSON manifests describing every PixelLab-generated atomic tile
1585| 3. **RoomAssembler** — templates that compose rooms from catalog assets with placement rules
1586| 
1587| ## 1. TileObjectStack
1588| 
1589| Replaces `ChunkData.building_tiles` (Dictionary of single entries) with a stacked object model.
1590| 
1591| ### Data Model
1592| 
1593| ```gdscript
1594| # One object on a tile
1595| class TileObject:
1596|     var asset_id: String       # e.g. "wood_plank_03"
1597|     var category: String       # "floor", "furniture", "item", "wall", etc.
1598|     var z_layer: int           # render order (0=ground, 1=floor, 2=furniture, 3=items)
1599|     var walkable: bool         # can the player walk on/through this?
1600|     var blocking: bool         # does this block movement?
1601|     var pickable: bool         # can the player pick this up?
1602|     var interactable: bool     # can the player use this (open, craft, sit)?
1603|     var provides: Array        # ["cooking", "sleeping", "storage"] — what this enables
1604|     var value: int             # trade/loot value
1605|     var properties: Dictionary # extensible: {locked: true, hp: 50, fuel: 10}
1606| 
1607| # Stack of objects at one tile position
1608| class TileStack:
1609|     var objects: Array = []    # ordered bottom-to-top [floor, rug, table, plate, spoon]
1610|     
1611|     func add(obj: TileObject) -> void
1612|     func remove(obj: TileObject) -> void
1613|     func top() -> TileObject               # topmost object
1614|     func is_walkable() -> bool             # true if no blocking object in stack
1615|     func get_interactables() -> Array      # all objects with interactable=true
1616|     func get_pickables() -> Array          # all objects with pickable=true
1617|     func get_by_category(cat: String) -> Array
1618| ```
1619| 
1620| ### Integration with ChunkData
1621| 
1622| Replace:
1623| ```
1624| var building_tiles: Dictionary = {}  # Vector2i → {type, material, z_index}
1625| ```
1626| 
1627| With:
1628| ```
1629| var tile_stacks: Dictionary = {}     # Vector2i → TileStack
1630| ```
1631| 
1632| BuildingCompiler stamps TileObjects instead of flat dictionaries. Walkability derived from stack contents (any blocking object = impassable).
1633| 
1634| ### Interaction Model
1635| 
1636| When player presses E at a tile:
1637| 1. Get TileStack at player's facing tile
1638| 2. Scan top-to-bottom for first interactable/pickable object
1639| 3. If pickable → add to inventory, remove from stack
1640| 4. If interactable → trigger interaction (open chest, use forge, sit in chair)
1641| 5. If nothing → "Nothing to interact with"
1642| 
1643| ### Rendering
1644| 
1645| DeferredRenderer paints tile stacks bottom-to-top onto layered images:
1646| - Z0 image: floors (wood_plank, stone_slab, dirt)
1647| - Z1 image: floor decorations (rugs, bloodstains, cracks)
1648| - Z2 image: furniture (tables, chairs, beds, forges)
1649| - Z3 image: items on surfaces (plates, books, tools)
1650| - Z4 image: walls (rendered at wall height)
1651| - Z5 image: roofs (alpha-fades on entry)
1652| 
1653| Each z-layer is one Image sprite per chunk (6 sprites instead of current 6). Performance identical to current system.
1654|

1755| ### PixelLab Generation Strategy
1756| 
1757| Generate assets in batches by category. Each batch:
1758| 1. Define palette + style constraints (medieval fantasy, 32x32, consistent lighting)
1759| 2. Generate 10-20 variants per sub-type
1760| 3. Download PNGs to `assets/catalog/<category>/`
1761| 4. Write manifest.json with properties
1762| 5. Verify visual consistency (size, palette, style)
1763| 
1764| Priority order for generation:
1765| 1. Terrain tiles (grass, water, sand, stone, paths) — highest visual impact
1766| 2. Wall tiles (wood N/S/E/W, stone N/S/E/W) — buildings need walls
1767| 3. Floor tiles (wood plank, stone slab) — building interiors
1768| 4. Door tiles — building entry points
1769| 5. Furniture (table, chair, bed, shelf, barrel) — interior life
1770| 6. Items (plate, book, candle, tool) — interactable objects
1771| 7. Nature (trees, bushes, flowers, rocks) — outdoor detail
1772| 8. Roof tiles — building canopy layer
1773| 9. Fixtures (forge, anvil, oven, well) — functional structures

1870| ## Integration with World Compiler
1871| 
1872| SettlementsLayer currently calls `BuildingCompiler.compile_building()`. The new flow:
1873| 
1874| 1. SettlementsLayer scores site, picks building type based on settlement tier
1875| 2. `RoomAssembler.assemble_building()` replaces `BuildingCompiler.compile_building()`
1876| 3. RoomAssembler stamps walls (from wall catalog), places door, lays floors
1877| 4. For each room in the building template, assembles furniture + items from catalog
1878| 5. All objects go into `ChunkData.tile_stacks[pos]` as TileObject instances
1879| 6. DeferredRenderer reads tile_stacks and paints z-layered images
1880| 
1881| ## Rendering Changes
1882| 
1883| DeferredRenderer currently paints building_tiles as single-color pixels. New approach:
1884| 
1885| **Phase 1 (colored pixels — current):** Paint tile stacks as colored pixels by category. Walls = brown, floors = tan, furniture = dark brown, items = yellow. Same visual as now but data model supports stacking.
1886| 
1887| **Phase 2 (PixelLab tiles):** Load actual textures from AssetCatalog. Paint 32x32 tiles from catalog onto per-z-layer images. Each tile position gets its stack rendered bottom-to-top across z-layer images.

1931| # Universal Tileset Framework — Wang Autotile Pipeline for All Visual Domains
1932| 
1933| **Date**: 2026-05-25
1934| **Status**: Active — supersedes color-algebra-tiles-design.md
1935| **Depends on**: World Compiler, TileObjectStack, GrainStack (L0), PixelLab MCP
1936| 
1937| ## Problem
1938| 
1939| The game needs seamless, layered, interactable visuals across multiple domains: natural terrain, man-made pathways, building interiors (floors, walls, roofs), lighting, and decorative objects. Each domain has its own palette of materials that transition into each other. Generating and managing these transitions manually is unsustainable.
1940| 
1941| ## Solution
1942| 
1943| A universal framework where every visual domain follows the same pipeline:
1944| 
1945| 1. **Define a palette chain** — ordered list of materials that transition into each other
1946| 2. **Generate Wang tilesets** — one per adjacent pair, chained via base_tile_id
1947| 3. **Store with manifests** — JSON metadata per tileset in `assets/catalog/<domain>/`
1948| 4. **Render by adjacency** — renderer checks neighbor tiles and picks the right Wang tile
1949| 5. **Layer domains** — terrain under pathways under floors under walls under roofs under lighting
1950| 
1951| PixelLab's `create_topdown_tileset` generates 16-23 autotiles per call with corner-based seamless transitions. Chaining via `base_tile_id` ensures visual consistency across the full palette.
1952| 
1953| ## The Framework
1954| 
1955| ### Step 1: Define Domain Palette Chain
1956| 
1957| Each domain is an ordered list of materials. Adjacent materials in the list get transition tilesets.
1958| 
1959| ```
1960| TERRAIN:   ocean → beach → grass → forest → stone → snow → lava → mystic
1961| PATHWAYS:  grass → dirt_trail → dirt_path → cobblestone → brick_road → marble_road
1962| FLOORS:    dirt → wood_plank → stone_slab → marble → carpet → ornate_tile
1963| WALLS:     exterior → wood_wall → stone_wall → brick_wall → marble_wall → ornate_wall
1964| ROOFS:     sky → thatch → wood_shingle → slate → clay_tile → copper
1965| LIGHTING:  darkness → torchlight → daylight → bright_sun → magical_glow
1966| ```
1967| 
1968| Each chain produces N-1 tilesets for N materials. Total per domain: ~5-8 tilesets.
1969| 
1970| ### Step 2: Generate Chained Wang Tilesets
1971| 
1972| For each adjacent pair in a chain:
1973| 
1974| ```
1975| tileset_1 = create_topdown_tileset(
1976|     lower_description="ocean water",
1977|     upper_description="sandy beach",
1978|     tile_size={"width": 32, "height": 32},
1979|     transition_size=0.25
1980| )
1981| # Wait for completion, get base_tile_id
1982| 
1983| tileset_2 = create_topdown_tileset(
1984|     lower_description="sandy beach",
1985|     upper_description="green grass",
1986|     lower_base_tile_id=tileset_1.upper_base_tile_id,
1987|     tile_size={"width": 32, "height": 32},
1988|     transition_size=0.25
1989| )
1990| # Chain continues...
1991| ```
1992| 
1993| Each tileset produces 16 tiles (or 23 at transition_size=1.0) with all corner combinations handled automatically.

2027| ### Step 4: Render by Adjacency (Wang Tile Selection)
2028| 
2029| For each tile position, the renderer:
2030| 
2031| 1. Sample the material at this tile and its 4 corner neighbors
2032| 2. Encode corners as a 4-bit index (each corner = material A or material B)
2033| 3. Look up the Wang tile for that index from the tileset
2034| 4. Paint onto the appropriate z-layer image
2035| 
2036| ```gdscript
2037| # Pseudocode for Wang tile selection
2038| func get_wang_tile_index(chunk, x, y, material_a, material_b) -> int:
2039|     # Sample 4 corners (top-left, top-right, bottom-left, bottom-right)
2040|     var tl = 1 if get_material(x-1, y-1) == material_b else 0
2041|     var tr = 1 if get_material(x, y-1) == material_b else 0
2042|     var bl = 1 if get_material(x-1, y) == material_b else 0
2043|     var br = 1 if get_material(x, y) == material_b else 0
2044|     return tl * 8 + tr * 4 + bl * 2 + br
2045| ```
2046| 
2047| This is the standard Wang/corner autotile algorithm. Each index maps to one of the 16 tiles in the tileset.
2048| 
2049| ### Step 5: Layer Domains (Z-Order)
2050| 
2051| | Z | Domain | Content | Driven By |
2052| |---|--------|---------|-----------|
2053| | -2 | Terrain | ocean, beach, grass, stone, snow | BiomeLayer (L6) |
2054| | -1 | Pathways | dirt paths, cobblestone roads | RoadsLayer (L10) + road_type |
2055| | 0 | Floors | wood plank, stone slab (inside buildings) | BuildingCompiler floor material |
2056| | 1 | Texture patterns | grass blades, pebbles, moss (transparent overlays) | VegetationLayer (L8) density |
2057| | 2 | Detail objects | flowers, leaves, small stones (non-interactive) | Biome + density rules |
2058| | 3 | Walls | wood, stone, brick (blocking) | BuildingCompiler wall material |
2059| | 4 | Interactable items | branches, herbs, loose stones (pickable) | Sparse RNG placement |
2060| | 5 | Large objects | trees, boulders, furniture | TileObjectStack blocking objects |
2061| | 6 | Roofs | thatch, shingle, slate (alpha-fades on entry) | BuildingCompiler roof material |
2062| | 7 | Lighting | darkness, torchlight, daylight overlays | DayNightCycle + light sources |

2064| ## Visual Domains — Detailed
2065| 
2066| ### Domain 1: Terrain (First Implementation)
2067| 
2068| **Palette chain:** ocean → beach → grass → forest_floor → stone → snow → lava → mystic_purple
2069| 
2070| **Tileset count:** 7 chained tilesets (ocean→beach, beach→grass, grass→forest, forest→stone, stone→snow, snow→lava... skip improbable pairs, only generate biome pairs that actually occur in the world)
2071| 
2072| **Practical optimization:** Not every pair needs a tileset. Only generate transitions for biome pairs that are actually adjacent in the compiled world:
2073| - ocean↔beach (always)
2074| - beach↔grass (always)
2075| - grass↔forest (always)
2076| - grass↔stone (mountains next to grassland)
2077| - stone↔snow (high elevation)
2078| - grass↔sand (savanna/desert edge)
2079| - water↔swamp (wetlands)
2080| 
2081| ~8 terrain tilesets × 16-23 tiles = ~130-180 tiles, ~8 PixelLab calls.
2082| 
2083| ### Domain 2: Pathways
2084| 
2085| **Palette chain:** natural_ground → dirt_trail → cobblestone → brick_road
2086| 
2087| **Tileset count:** 3 chained tilesets
2088| 
2089| Roads in the compiled world have a `road_type` value (1=trail, 2=road). The renderer uses the appropriate pathway tileset based on road_type and the surrounding terrain.
2090| 
2091| ### Domain 3: Building Floors
2092| 
2093| **Palette chain:** dirt → wood_plank → stone_slab → marble → carpet
2094| 
2095| **Tileset count:** 4 chained tilesets
2096| 
2097| Interior floors transition between room types — a kitchen (stone_slab) meeting a bedroom (wood_plank) gets a smooth transition tileset.
2098| 
2099| ### Domain 4: Walls
2100| 
2101| Walls are different from terrain — they're vertical surfaces rendered at an angle. Use `create_tiles_pro` with `low top-down` view for wall tiles that show height.
2102| 
2103| **Types:** wood_wall, stone_wall, brick_wall, each with N/S/E/W facing variants.
2104| 
2105| Wall tiles include: solid wall, wall with window, wall with door frame, corner piece, end piece.
2106| 
2107| ### Domain 5: Roofs
2108| 
2109| Roof tiles rendered at `low top-down` view showing the roof surface.
2110| 
2111| **Types:** thatch, wood_shingle, slate, clay_tile
2112| 
2113| Each roof type gets edge tiles (ridge, eave, corner) for natural-looking roof shapes.
2114| 
2115| ### Domain 6: Lighting
2116| 
2117| Transparent overlay tiles that modify the brightness/color of everything below.
2118| 
2119| **Types:** full_darkness, dim_shadow, ambient_light, bright_light, warm_torchlight, cool_moonlight, magical_glow
2120| 
2121| Applied as a top-layer image that modulates based on time of day, light sources (torches, windows, campfires), and interior/exterior status.
2122| 
2123| ## Grain Stack Binding (Digging)
2124| 
2125| The terrain tileset layer is bound to the GrainStack:
2126| - Top grain determines which terrain material is displayed
2127| - Digging pops the top grain → material changes → tileset re-renders
2128| - Exposed material = next grain in the stack (grass → soil/earth → stone → bedrock)
2129| 
2130| The renderer watches for grain stack changes and re-renders affected tiles.
2131| 
2132| ## Animation
2133| 
2134| Every tileset and object gets animated variants via PixelLab's animation tools:
2135| - Water tiles: flowing/ripple animation (animate_object or frame variants)
2136| - Grass texture patterns: wind sway
2137| - Lava tiles: flowing/bubbling
2138| - Torch/fire lighting: flicker
2139| - Door objects: open/close states (create_object_state)
2140| 
2141| Animations stored as frame sequences in the manifest. Renderer cycles frames based on a global animation timer.

2182| ## TilesetRenderer Class
2183| 
2184| Replaces current DeferredRenderer terrain painting. New class that:
2185| 1. Loads all domain manifests from `assets/catalog/`
2186| 2. For each chunk, determines which tilesets are needed (based on biome adjacencies)
2187| 3. Paints Wang tiles onto per-z-layer images using the 4-corner index algorithm
2188| 4. Layers all domain images bottom-to-top
2189| 
2190| ```gdscript
2191| class TilesetRenderer:
2192|     var _catalog: AssetCatalog
2193|     var _tilesets: Dictionary = {}  # "ocean_to_beach" → {tiles: [Image], ...}
2194|     
2195|     func render_terrain_layer(chunk: ChunkData, size: int) -> Image
2196|     func render_pathway_layer(chunk: ChunkData, size: int) -> Image
2197|     func render_floor_layer(chunk: ChunkData, size: int) -> Image
2198|     func render_wall_layer(chunk: ChunkData, size: int) -> Image
2199|     func render_roof_layer(chunk: ChunkData, size: int) -> Image
2200| ```
