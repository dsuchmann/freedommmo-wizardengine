Façade "Lego-Block" model — schematic sketch (no PixelLab yet)

Quantum: PixelLab max object = 400×400 px = 12.5 tiles @ 32 px/tile. One block = ONE FLOOR of ONE building SECTION, ≤ ~12×12 tiles, generated per biome × material × variant × shape, in a WITH-ROOF (standalone small building) and NO-ROOF (assemblable piece) version. Background must be keyed transparent.

View: all blocks are ¾ top-down, SOUTH-facing — never isometric by default (iso reserved selectively, to give certain shapes more expression). You only ever see the south wall outside and the north wall inside. Every block ships metadata (door + window tile-rects, measured from the art) so the game knows where to walk in and where to hang the door-leaf. A library = a set of shapes per biome × material × variant.

1 · One block, two versions

WITH roof → drop-in single-story building
NO roof → a piece to tie to other pieces
A block carries its material (stone/timber/…), its apertures (door + windows), and a shape. The no-roof version exposes a clean top edge so a shared roof can flow over it, and clean side edges so it abuts the next section. The with-roof version is the whole building when one section is enough.

2 · Block palette — shapes that abut (no-roof pieces)

front-entry (rect): 2 windows · door · window
wing (rect)
portico (curved / half-round)

3 · Assembled building — NO-ROOF blocks + ONE unified roof flowing over all sections

Sections placed by footprint (front south, wing east, portico north = "deeper inside"). The roof is a single continuous surface over the union — this is the procedural roof engine path (handles any section shape).

4 · Assembled building — WITH-ROOF blocks stamped together (matching roofs flow seam-to-seam)

Same sections, each carrying its own roof of the same family; where they meet, ridges/eaves line up. This is the generated-roof-block path — to compare against #3.

5 · Stacking — floors are blocks too (up to 10+ stories)

A multi-story building = NO-ROOF floor-blocks stacked vertically (walls + caps aligned); only the TOP gets a roof, the ground floor carries the door. Same block model, vertical axis.

6 · Exterior = SOUTH wall · Interior = NORTH wall · the door

Outside you only ever see the south wall; inside, the north wall + a perimeter (the existing floor-tile + interior-wall system), shaped to mirror the section. Each block's metadata records the door + window tile-rects (measured from the art) → the game knows where to walk in and where to hang the door-leaf overlay.

EXTERIOR — south wall + door metadata anchor (red)
INTERIOR — north wall + perimeter + floor (existing system)

7 · Foundations don't stack — generate COMPLETE, decompose into pieces

Generate the COMPLETE building (roof + wall + foundation), then split it at measured lines into a roof-cap (top only), a wall-slice (the tileable floor — no roof, no foundation), and a foundation-course (base only). Assemble per the placement metadata's floor count: foundation @ base · wall-slices stacked · roof @ top. The slice is cropped from the same art, so it tiles seam-clean and matches the material exactly.

9 · Depth — the front is a facade, the DEPTH is roof (rear walls never seen)

A 10-wide × 100-deep building: outside you see ONLY the south facade + a long roof. The rear is interior (occluded); E/W + back walls are never seen outside. Depth is a roof problem — generate the south facade ONCE, cover the depth with roof (procedural handles any depth; or roof blocks tiled north). Never stamp a facade you can't see.

PLAN (top-down) — only the south edge is a facade
¾ VIEW — south facade + long roof; rear hidden
3 axes:
• WIDTH (E-W) → facade blocks tiled across the south edge
• DEPTH (N-S) → roof (procedural, or roof blocks tiled north)
• HEIGHT (stories) → wall-slices stacked + roof on top

Generate a facade at every exposed south edge; everything else is roof.

10 · Door detection — detect-at-AUTHORING (beauty-first, deterministic at runtime)

Generate freely for beauty (porches, jutting roofs, off-center doors). Once per library asset, a vision pass locates the door / windows / entry and writes them to metadata — cost is one-time per asset, NOT per placement. The game reads metadata; it never guesses. Blueprint feeds prompt guidance (door count, role, grandeur), not coordinates.

11 · Scaling up — a 2000×2000 castle is the SAME primitives, more sections

Yes, the renderer can paint it. A castle is just ONE building with a very complex multi-section footprint: a keep + towers (tall slice-stacks), great hall + chapel (facade + roof), curtain walls (facade tiled E-W), a gatehouse (the main door), and open courtyards (no roof). Every exposed south edge → facade; everything else → roof; towers → tall stacks; courtyards → holes. The renderer iterates sections — it never makes a 2000×2000 image, so scale is free. The only new work is a BLUEPRINT generator for huge complex structures — the current system makes cities as separate district buildings; a castle is "one building" with a sprawling footprint. The painting is already covered.

12 · How the seams hold (the contract)

• Vertical joins (wall ↔ wall): identical material body + a strong top cap/cornice reads as a molding and hides the join.
• Corners / E-W faces: dedicated edge pieces (the face the building "turns into") — the real 3D edge, like the stone_160 8-direction set.
• Roof: option A one shared surface (procedural); option B matching roof blocks whose ridge+eave heights are authored to align.
• Interior: unchanged — it's already built from the same footprint sections, so it matches whatever we assemble.
